최근 Aurora PostgreSQL을 업그레이드 했는데, 이 과정에서 필수로 ANALYZE를 진행해야 하는 프로세스가 있었습니다.

이것을 정리하면 좋을 것 같아, ANALYZE와 항상 함께 나오는 VACUUM도 함께 정리해보려고 합니다.

PostgreSQL을 다루는 첫 포스팅인 만큼, PostgreSQL이 어떤 데이터베이스인지부터 간단히 살펴본 뒤, VACUUM의 개념과 필요성, 방치했을 때 생기는 문제, Autovacuum의 동작 원리를 정리하고 마지막으로 직접 테스트해보는 것까지 공부해보겠습니다.

### PostgreSQL 이란?

PostgreSQL은 1986년 버클리 대학의 POSTGRES 프로젝트에서 출발한 오픈소스 객체-관계형 데이터베이스(Object-Relational DBMS)입니다.

상용 DBMS에 준하는 기능을 무료로 제공하면서도, 표준 SQL 준수와 안정성이 높아 금융권부터 스타트업까지 폭넓게 사용되고 있습니다.

PostgreSQL의 주요 특징은 다음과 같습니다.

*   MVCC (Multi-Version Concurrency Control) 기반의 동시성 제어로, 읽기와 쓰기가 서로를 막지 않습니다.
*   Extension 구조를 통해 PostGIS(공간 데이터), pgvector(벡터 검색) 등으로 기능을 확장할 수 있습니다.
*   다양한 데이터 타입(JSONB, 배열, 사용자 정의 타입 등)과 풍부한 인덱스 타입(B-tree, GIN, GiST, BRIN 등)을 지원합니다.
*   ACID 트랜잭션을 완전하게 보장합니다.
*   표준 SQL을 사용하여 Oracle과의 뛰어난 호환성을 보여줍니다. 

이 중에서도 VACUUM과 직접 연결되는 것이 바로 MVCC입니다.

PostgreSQL이 동시성을 처리하는 방식 자체가 VACUUM을 필요하게 만들기 때문입니다.

### Vacuum 이란?

Vacuum은 영어 단어 그 자체로, 진공, 공백, 청소 등 진공 청소기라는 의미를 가지고 있습니다. 

이와 같이 Vacuum을 쉽게 설명하면 PostgreSQL의 청소 작업입니다.

MVCC 구조에서 생기는 불필요한 데이터(dead tuple)를 정리하고, 데이터베이스가 정상적으로 동작하도록 유지하는 역할을 합니다.

VACUUM이 수행하는 일은 크게 4가지로 정리할 수 있습니다.

*   dead tuple을 제거하여 공간을 재사용 가능한 상태로 회수합니다.
*   인덱스에 남아있는 죽은 엔트리를 정리합니다.
*   오래된 row를 freeze 처리하여 Transaction ID Wraparound를 예방합니다.
*   ANALYZE를 함께 수행하면 옵티마이저 통계를 갱신합니다.

여기서, 일반 Vacuum은 공간을 재사용 가능한 상태로 만들 뿐 운영체제(OS)에 물리적으로 반환하지는 않는다는 것입니다. 테이블의 실제 파일 크기를 줄이려면 Vacuum Full (테이블 전체를 재작성하며 강한 잠금이 걸림)이나 pg\_repack(온라인으로 수행 가능) 같은 별도의 작업이 필요합니다. 일상적인 관리는 일반 VACUUM의 영역입니다.

참고로 Vacuum Full 작업은 운영 데이터베이스에서 수행시 DB를 사용하지 못하는 락 상태가 되므로 작업이 없는 시간대나, 새벽 다운타임을 확보할 수 있을때 진행해야합니다. 또한, 일반 Vacuum과는 달리 Vacuum Full은 동작 테이블을 Copy 하는 형식으로 진행하여 디스크를 충분히 확보한 상태에서 작업해야합니다.

이러한 이유들로 Full Vacuum의 경우는 운영시간대에서는 충분한 고려 없이 진행할 수 없는 작업입니다. 

### Vacuum이 필요한 이유

Vacuum 작업이 왜 필요한지를 이해하려면 PostgreSQL 에서 중요한 MVCC의 동작 방식을 먼저 알아야 합니다.

PostgreSQL은 UPDATE나 DELETE를 수행해도 기존 row를 즉시 물리적으로 삭제하지 않습니다.

*   UPDATE를 하면 기존 버전을 죽은 것으로 표시하고, 새로운 버전을 별도의 위치에 추가합니다.
*   DELETE를 하면 row를 죽은 것으로 표시만 하고 공간은 그대로 남겨둡니다.

이렇게 남겨진 죽은 버전을 dead tuple이라고 부릅니다. 다른 트랜잭션이 아직 그 버전을 참조하고 있을 수 있기 때문에 즉시 삭제하지 못하는 것이며, 이는 오류가 아니라 MVCC 구조에서 필연적으로 발생하는 부산물입니다.

문제는 이 dead tuple을 정리하지 않으면 성능에 저하가 유발 되고, 그것을 방지하기 위해 진행하는 것이 Vacuum입니다. 

만약 Vacuum이나 Auto Vacuum을 진행하지 않는다면, 아래와 같은 3가지의 문제가 발생할 수 있습니다. 

첫 번째, 테이블 비대화입니다.

*   dead tuple이 정리되지 않으면 테이블과 인덱스의 물리적 크기가 계속 커집니다.
*   row 수는 그대로인데 스캔해야 할 페이지가 늘어나므로, 동일한 쿼리의 I/O 부담이 커지고 캐시 효율이 떨어집니다.

두 번째, 통계 정보의 노후화입니다.

*   Autovacuum은 Vacuum 뿐 아니라 Analyze(옵티마이저 통계 수집)도 함께 수행합니다.
*   이 작업이 멈추면 옵티마이저 통계가 낡아져, 플래너가 잘못된 실행 계획을 선택하게 됩니다.
*   그 결과 갑작스러운 플랜 변화로 인한 고 CPU와 응답 지연이 발생할 수 있습니다.

세 번째, Transaction ID 랩어라운드 (Wraparound) 입니다.

*   PostgreSQL은 트랜잭션을 32비트 정수 ID(XID)로 추적하는데, 약 21억개를 사용하면 값이 한 바퀴를 돌게 됩니다.
*   이 경우 Read-Only 로 데이터베이스가 전환되거나 서비스가 중단될 수 있고, 올바른 데이터를 조회하지 못하게 됩니다.
*   이 현상을 방지하기 위해선 Auto Vacuum 이나, 정기적인 Vacuum 작업을 통해 정리가 필요합니다. 
*   만약, XID age가 autovacuum\_freeze\_max\_age(기본값 2억)에 도달하면, Autovacuum을 꺼두었더라도 wraparound 방지용 Autovacuum이 강제로 실행됩니다.

여담으로 트랜잭션 랩 리미트 상황은 PostgreSQL 깃허브 소스코드에서 where the world ends라는 코멘트로 정의하고 있습니다.

### Autovacuum의 동작 원리

PostgreSQL 에서는 이를 방지하기 위해 Auto Vacuum을 지원하고 있습니다.

```
threshold = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × numble_of_tuples
          = 50 + 0.2 × (테이블 행 수)
```

numble\_of\_tuples 는 pg\_class.reltuples 입니다. 

ALTER 명령어를 활용하여 테이블에 쓰임과 사이즈에 맞게 Auto Vacuum 값을 설정할 수 있습니다.

```
ALTER TABLE test.orders SET (
  autovacuum_vacuum_scale_factor = 0.02,   -- 20% → 2%
  autovacuum_vacuum_threshold    = 1000,
  autovacuum_vacuum_cost_limit   = 2000    -- 처리량 확보 (기본 200)
);
```
