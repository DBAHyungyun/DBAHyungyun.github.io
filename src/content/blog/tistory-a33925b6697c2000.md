## MVCC란 무엇인가?

우선 짧게, 지난번에 포스팅했던 글을 복습하자면

MVCC (Multi-Version Concurrency Control) 란, Data를 수정, 삽입하고 있는 상황에서는 트랜잭션이 종료될 때까지 대기했어야만 했습니다. 이러한 대기 상황은 성능을 저하시켰고 이렇게 성능이 저하되는 경우 즉, Lock이 없이 다른 트랜잭션이 수행되는 중에도 읽기, 쓰기 작업을 동시에 처리할 수 있게하여 동시성을 향싱시키는 제어 방법입니다. 

Lock 잠금 없이 다중 트랜잭션이 접근할 수 있다면, 도대체 Lock은 어떤 상황에서 발생하게 되는건지, 이와 관련된 트랜잭션은 무엇인지 공부해보려 합니다. 

## Lock 과 트랜잭션이란 ?

Lock은 트랜잭션과 서로 비슷한 개념인 것 같지만, 잠금은 동시성을 제어하는 기능이고 트랜잭션은 데이터의 정합성을 보장하기 위한 기능이다. 

트랜잭션은 논리적인 작업 단위가 모두 적용 되거나, 모두 적용되지 않거나 한다는 원자성을 기반으로 하는 데이터 정합성을 위한 기능이다. 만약, 10개의 쿼리로 묶여져 있는 하나의 트랜잭션 이라면 해당 트랜잭션은 쿼리가 모두 성공하거나, 모두 실패하거나 하는 매커니즘을 따르게 됩니다. (이외에도 ACID, 원자성, 일관성, 고립성, 지속성이 있습니다.)

Lock (잠금)은 여러 커넥션, 쿼리 등 동시에 동일한 데이터로 접근할 때, 데이터의 정합성에 문제가 발생하지 않도록 접근 순서를 물리적으로 제어하는 동시성 제어의 형태를 띄는 동시성 제어 장치이다.

### Lock의 종류

MySQL 의 Lock 에는 크게 MySQL 엔진의 Lock , MySQL 스토리지의 Lock 으로 구분할 수 있으며,

MySQL 엔진 레벨의 Lock은 모든 스토리지 엔진, 서버 전체, 테이블 전체에 영향을 미치는 넓은 범위의 Lock이다.

MySQL 스토리지 레벨의 Lock은 InnoDB 엔진 내부에서 행 (Row) 단위로 정교하게 수행되는 Lock 이다.

오늘은 이 Lock의 종류중에서 MySQL 엔진의 Lock인 글로벌 락, 테이블 락, 네임드 락, 메타데이터 락에 대해서 알아보려고 합니다.

### Global Lock?

글로벌 락은 MySQL 서버 전체에 해당하는 Lock 이며 MySQL 에서 제공하는 잠금 가운데 가장 큰 범위를 가지고 있다. 일반적으로 작업 대상 테이블이나 데이터베이스가 다르더라도 동일한 엔진이라면 해당 잠금이 모든 데이터베이스에 영향을 미친다.

여러 데이터베이스에 존재하는 MyISAM 이나 MEMORY 테이블에 대해 mysqldump로 일관된 백업을 받아야 할 때는 글로벌 락을 사용해서 백업을 수행한다. 

일반적으로, 특정 세션에서 백업 락을 획득하면 모든 세션에서 다음과 같이 테이블의 스키마나 사용자의 인증 관련 정보를 변경할 수 없게 된다.

*   데이터베이스 및 테이블 등 모든 객체생성 및 변경 삭제
*   Repair Table 과 Optimize Table 명령
*   사용자 관리 및 비밀번호 변경

하지만, 백업 락은 일반적인 테이블의 데이터 변경은 허용된다. 

명령어 : FLUSH TABLES WITH READ LOCK; / UNLOCK INSTANCE;

단, AWS Aurora MySQL 에서는 admin 에게 SUPER USER 즉, 모든 권한을 부여하지 않는다. 그렇게 되면 mysqldump를 수행할 당시에 내부적으로 수행되는 Global Lock 에 대해서 권한이 없어 진행되지 않습니다.

이럴 때에는 mysqldump 명령어에서 명시적으로 --set-gtid-purged=OFF 옵션을 추가하여, mysqldump가 글로벌 락을 획득하지 못하도록 명령어를 수행해주어야 한다.

```
mysqldump --single-transaction --set-gtid-purged=OFF -h {aurora-endpoint} -u root -p 데이터베이스명 > backup.sql
```

### Table Lock ?

테이블 락은 개별 테이블 단위로 설정되는 잠금이며, 명시적 또는 묵시적으로 특정 테이블에 대한 락을 획득할 수 있다. 테이블 락은 MyISAM 뿐 아니라, InnoDB 스토리지 엔진에서도 동일하게 설정할 수 있지만 일반적인 상황에서는 명시적으로 테이블을 잠그는 작업이기에 온라인 작업에서 사용할 일이 존재하지 않는다. 

일반적으로 명령어에 나와있는 대로 Read, Write 라고 해서 Read는 SELECT 구문이 수행되지 않는 읽기 잠금이고, Write 는 UPDATE, INSERT 등 Write 작업이 되지 않는 경우라고 생각하기 쉽습니다.

하지만, READ 락은 공유 락 (Shared Lock) 으로 나를 포함한 다른 커넥션 및 사용자가 SELECT 하는 것을 허용하는 명령어 입니다.

WRITE 락은 배타적 락 (Exclusive Lock) 으로 내가 테이블을 독점해서 점유하고 싶을때 사용하는 락입니다. 나를 제외한 모든 커넥션 및 사용자는 해당 테이블에 조회는 물론 수정,삽입 모두 불가능한 상태가 됩니다.

LOCK TABLES 'table\_name' \[READ\] : 공유 잠금

LOCK TABLES 'table\_name' \[WRITE\] : 나를 제외한 모든 커넥션 및 사용자 잠금

명령어 : LOCK TABLES 'table\_name' \[ READ | WRITE\] / UNLOCK TABLES

### Named Lock?

네임드 락은 GET\_LOCK() 함수를 이용해 임의의 문자열에 대해 잠금을 설정할 수 있다. 네임드 락은 대상이 테이블이나 레코드 또는 AUTO\_INCREMENT와 같은 데이터베이스 객체가 아니라는 것이다. 네임드 락은 단순히 사용자가 지정한 문자열 (String) 에 대해 획득하고 반납 (해제) 하는 잠금이다.

예를 들어, "mylock" 이라는 문자열에 대해 잠금을 획득하고자 한다면, 아래와 같은 방법으로 획득할 수 있다.

```
-- 이미 잠금을 사용 중이면 2초 동안만 대기한다.
SELECT GET_LOCK('mylock',2);

-- mylock 이라는 문자열에 대해 잠금이 설정돼 있는지 확인한다.
SELECT IS_FREE_LOCK('mylock');

-- mylock 이라는 문자열에 대해 획득했던 잠금을 반납(해제) 한다.
SELECT RELEASE_LOCK('mylock');

-- 3개 함수 모두 정상적으로 락을 획득하거나 해제한 경우에는 1을, 아닌 경우에는 0을 반환한다.
```

또한, 네임드 락의 경우에는 많은 레코드에 대해서 복잡한 요건으로 레코드를 변경하는 트랜잭션에 유용하게 사용할 수 있다. 

예를 들어, 선착순 쿠폰 발급 이벤트 처럼 여러 웹 서버가 동시에 접근하는 동시성 이슈를 막기 위해 분산 락을 구현할 때 사용하거나, 배치 프로그램 처럼 한번에 많은 레코드를 변경하는 경우 실행 시간을 분산하거나 프로그램의 코드를 수정해서 데드락을 최소화 하는 방향으로 사용한다.

MySQL 8.0 이상 버전에서는 네임드 락을 중첩해서 사용할 수 있게 되었으며 현재 세션에서 획득한 네임드 락을 한번에 해제하는 기능도 추가 됐다.

```
SELECT GET_LOCK('mylock_1',10);
-- mylock_1 에 대한 작업 실행

SELECT GET_LOCK('mylock_2',10);
-- mylock_1 과 mylock_2 에 대한 작업 실행

SELECT RELEASE_LOCK('mylock_2');
SELECT RELEASE_LOCK('mylock_1);

SELECT RELEASE_ALL_LOCKS();
-- mylock_1 과 mylock_2 를 동시에 모두 해제하는 명령어 RELEASE_ALL_LOCKS() 함수
```

### MetaData Lock?

메타데이터 락은 데이터베이스 객체 (대표적으로 테이블이나 뷰 등)의 이름이나 구조를 변경하는 경우에 획득하는 잠금이다. 명시적으로 사용자가 획득하거나 해제할 수 있는 잠금이 아니라, ALTER TABLE 등을 실행할 때 DB가 스스로를 보호하기 위해서 묵시적으로 수행하는 잠금이다.

RENAME TALBE tab\_a TO tab\_b 같이 테이블 이름을 변경하는 경우 자동으로 잠금을 획득하고, tab\_a, tab\_b 모두 잠금을 획득한다. (원본 이름과 변경될 이름 모두 한꺼번에 잠금 획득)

이런 경우에 트래픽이 많은 테이블에서 트랜잭션이 열려있는 상태로 ALTER TABLE ADD 로 컬럼을 추가하는 경우에 기존 트랜잭션이 끝나기 전에는 대기가 지속되므로 메타데이터 락 상태로 지속되게 됩니다. ALTER TABLE이 뒤에 발생하는 쿼리들을 수행하지 못하도록 막으면서 DB에 부하가 생기는 경우도 존재하니, 수행한 트랜잭션은 꼭 짧게 유지하고 DDL 작업은 트래픽이 적은 새벽시간에 작업해야 합니다.

```
RENAME TABLE rank TO rank_backup;
RENAME TABLE rank_new TO rank;
```
