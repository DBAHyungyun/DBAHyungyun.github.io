오늘은 SQL 튜닝에서 SQL 처리 과정과 I/O 에 대해서 공부해보고 기록해보려 합니다.

SQLP를 준비하는 과정에서 친절한 SQL 튜닝 서적과 개인적으로 찾아보고 공부한 자료들을 바탕으로 공부하였으니 이점 참고 부탁드리겠습니다. 

Database는 Oracle을 기준으로 작성하였습니다. 

* * *

## SQL 처리 과정 이란?

사용자가 만약 아래와 같은 쿼리를 수행하면 DB 내부에서는 크게 4단계의 과정을 거치며 데이터를 가져옵니다. (친절한 SQL 튜닝 책에서는 3단계의 과정을 거칩니다. 마지막 실행 엔진으로의 데이터 추출은 참고 부탁드립니다.)

```
SELECT * FROM users WHERE id = 1;
```

1.  SQL 파싱 
2.  SQL 최적화 (옵티마이저)
3.  로우 소스 생성
4.  실행 엔진으로 데이터 추출

위의 4가지 순서를 거치며 SQL 이 실행 되고 데이터가 추출됩니다. 지금부터 위 과정을 자세히 살펴보도록 하겠습니다.

### SQL 파싱

SQL 파싱은 사용자로부터 SQL을 전달 받으면 가장 먼저 진행하는 과정이다. SQL 구문이 실행되면 파서는 3가지 과정을 통해 실행 가능한 SQL 구문인지 판단합니다. 

1.  파싱 트리 생성 : SQL 문을 이루는 개별 구성요소를 분석해서 파싱 트리 생성합니다.
2.  Syntax 체크 (문법 검사) : 문법적인 오류가 없는지 확인합니다. 예를 들어, SELET \* FROM user; 라는 쿼리는 파서가 SELECT 의 오타임을 확인하고 Syntax Error 를 출력하게 됩니다.
3.  Semantic 체크 (의미 검사) : 문법적인 오류가 없는지 확인 했다면, 의미상의 오류가 없는지 확인합니다. 예를 들어, 조회한 쿼리문에서 실제 테이블이 존재하는지, 실제 존재하는 오브젝트를 조회하는지 여부를 확인하고 실제 데이터가 없다면 에러 메세지를 출력합니다.

이 3가지 과정을 거친 후, 실행된 SQL 텍스트가 캐시 (메모리) 영역에 저장되어 있는지 확인합니다.

*   하드 파싱 (Hard Parsing) : 캐시 영역을 확인했는데, 실행된 이력이 없는 처음보는 쿼리에서 발생합니다. 이 경우에는 옵티마이저가 해당 쿼리에 대해서 실행 계획을 세우게 되고, 로우 소스 생성을 거쳐 SQL을 실행합니다. 다만, 이 과정에서 과도하게 자원을 사용하여, Database에 부하를 발생시킬 수 있습니다.
*   소프트 파싱 (Soft Parsing) : 캐시 영역을 확인했을 때, 실행된 이력이 있는 경우 캐시 (메모리) 영역에서 데이터를 가져와 실행합니다. 이 경우에는 하드 파싱과 비교하여 자원 사용량이 낮고, 부하를 발생 시킬 가능성이 적습니다. SQL 튜닝 포인트 중 하나입니다.

일반적으로 Literal SQL 즉, 상수값을 사용하는 SQL 인 경우에는 하드 파싱을 사용합니다. 동일한 구조의 쿼리문에서 특정 상수값만 변경되어 수행된다면, 불필요한 하드 파싱이 수행되므로 상수값에 바인드 변수를 설정하여 과도하게 늘어나는 하드 파싱을 방지할 수 있습니다.

### SQL 최적화 (옵티마이저)

SQL 옵티마이저는, 사용자가 원하는 작업을 가장 효율적으로 수행할 수 있는 최적의 데이터 액세스 경로를 선택해주는 DBMS의 핵심 엔진입니다.

쉽게 예를 들어, 우리가 서울에서 부산까지 간다고 가정할 때, 고속도로를 탈 수도 있고, 국도를 탈 수도 있고, KTX나 비행기를 탈 수도 있습니다. 목적지는 같지만 가는 방법(경로)은 수십 가지입니다. 이런 여러가지 경로속에서 가장 최적의 효율적인 경로를 찾아주는 것이 SQL 옵티마이저의 역할입니다. 

옵티마이저의 최적화 단계를 3단계로 요약하자면,

1.  사용자로부터 전달받은 쿼리를 수행하는 데 후보군이 될 만한 실행계획들을 찾아낸다.
2.  데이터 딕셔너리 (Data Dictionary) 에 미리 수집해 둔 오브젝트 통계 및 시스템 통계 정보를 이용해 각 실행계획의 예상 실행 비용을 산정한다.
3.  최저 비용을 나타내는 실행계획을 선택한다.

이렇게 옵티마이저는 최적의 자원만을 사용하며 데이터를 조회할 수 있는 최적화 방안을 도출하여 사용자에게 제공합니다.

이때 비용 기반 옵티마이저인 CBO (Cost-Based Optimizer) 방식으로 최소 비용을 선택하여 실행 계획을 도출합니다. 이때, Disk I/O, CPU Utilization, Memory Usage 등 여러 지표를 확인하게 되는데 이 과정속에서 잘못된 통계정보를 가지고 있는 경우 잘못된 실행 계획을 도출 할 수도 있습니다.

네비게이션의 소프트웨어 업데이트를 미뤄오다, 새로 생긴 빠른길이 아닌 오래된 길을 안내하듯 Database도 마찬가지로 오랜 기간 동안 통계 정보에 대한 갱신이 없다면, 더 효율적인 실행 계획이 아닌 잘못된 실행 계획을 도출 할 수 있습니다.

이런 개념들을 참고해서 옵티마이저를 너무 맹신하게 되면 안된다고 생각합니다.

### 로우 소스 생성

마지막, 로우 소스 생성의 단계에서는 SQL 옵티마이저가 선택한 실행 경로를 실제 실행 가능한 코드 또는 프로시저의 형태로 포맷팅한다. 로우 소스 생성기 (Row-Source Generator)가 그 역할을 맡으며, 쉽게 생각하면 인터프리터 처럼 실행 가능한 포맷으로 소스를 생성한다고 보면 될 것 같습니다.

그 이후에는 SQL 구문이 실행되며 원하는 데이터를 색인 할 수 있을 것입니다.

## 결론

이렇게 SQL 처리 과정에 대해서 공부해보았습니다. 튜닝에서 굉장히 중요한 부분이자 기초가 되는 부분으로 가장 많이 접하게 될 부분이자 친숙해야할 부분이라고 생각합니다.

위 본문에서 작성한대로 항상 옵티마이저가 옳은 판단을 내리는것은 아닙니다. Index 역시 항상 생성해주는것이 정답은 아닌 경우도 있습니다. 다음에는 이런 경우들을 좀 더 심화해서 공부해보고, Physical I/O, Logical I/O 에 대해서 공부해보겠습니다.
