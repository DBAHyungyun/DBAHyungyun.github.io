## 개요

데이터베이스 테이블에서 데이터를 찾는 방법은 크게 두가지로 나뉘어 생각할 수 있습니다.

*   테이블 전체를 스캔한다. (Table Full Scan)
*   인덱스를 이용한다. (Index Range Scan)

Index는 항상 SQL 튜닝에서 중요한 포인트를 차지하는 부분입니다. 하지만, 무분별한 인덱스 생성은 되려 SQL 성능을 저하시키는 원인이 될 수 있습니다.

그리고, Table Full Scan 이라고 해서 항상 성능에 좋지 않은 것은 아닙니다. 필요에 따라서는 Table Full Scan이 더 효율적인 SQL 성능을 발휘할 수도 있습니다. 

보통 인덱스 스캔의 경우에는, 큰 테이블에서 소량의 데이터를 검색할 때 사용하며, 온라인 트랜잭션 처리 (Online Transaction Proccessing, OLTP) 시스템 에서는 소량의 데이터를 주로 검색하므로 인덱스 튜닝이 무엇보다 중요합니다.

아래 Plan을 확인하면 users 라는 테이블을 Full Scan 하고 있으며, 이에 511,944 라는 비용을 지불함을 알 수 있습니다. 대용량의 테이블에서 모든 데이터를 다 뒤져보면서 찾아내는 것처럼 보입니다. 

여기서 인덱스를 생성하면, 큰 테이블에서 소량의 데이터를 찾아내는 작업을 하면서 Index가 존재하지 않으므로 생성해주는 것이 효율적인 튜닝 방법으로 보입니다.

SELECT 구문의 Where 조건절에 존재하는 user\_name 컬럼을 인덱스 컬럼으로 설정하고, Index를 생성해줍니다.

간단하게 Index는 기본적으로 B-Tree 형태로 가장 왼쪽 즉, 선두에 있는 기준부터 데이터의 위치가 정렬되기 때문에 조건절에 선두 컬럼이 위치 하느냐 위치하지 않느냐도 굉장히 중요합니다. 

우선 아래와 같이 조건절의 선두 컬럼에 해당하는 인덱스를 생성해 줍니다. 

```
-- user_name 컬럼에 인덱스 생성
CREATE INDEX idx_user_name ON users(user_name);
```

인덱스를 생성해준 뒤, 동일한 쿼리를 수행하면 아래와 같이 Index lookup on users 라고 출력이 되며 idx\_user\_name 인덱스를 사용해 Data를 읽어온 것으로 보입니다. Cost는 16.5 만큼만 사용하며 성능적으로 개선된 모습을 볼 수 있습니다.

그렇다면 위에서 간단하게 살펴 보았던 Index 선두 컬럼은 왜 중요한 것인가 할텐데 이 부분을 자세히 알아보겠습니다.

### Index 선두 컬럼의 중요성

B-Tree 형태는, 데이터가 정렬된 상태로 유지가 되어 있습니다. 우리가 지정한 컬럼 (Index 컬럼) 을 기준으로 오름차순, 혹은 내림차순으로 정리하여 정렬하고 있습니다. 

하지만, 이 정렬 규칙에서도 인덱스는 항상 가장 왼쪽 (선두)에 있는 기준부터 먼저 정렬하고 그 값이 같을때에만 그 다음 값인 오른쪽을 기준으로 정렬하게 됩니다. 

![](__MEDIA__/ee905d362004dfce7d046560864edf7852ac7c85c91bbf58893c81c18b409fa9.png)

Index B-Tree 형태

이런 규칙을 생각해서, 만약 (부서, 이름) 순서로 결합된 결합 인덱스를 생성했다고 가정해봅시다. 그럼 인덱스 선두 컬럼은 부서가 될테고 그 다음 이름이 후순위 컬럼이 됩니다. 이런 인덱스에서는 데이터가 아래와 같이 정렬되어 있습니다.

```
개발팀 - 김철수
개발팀 - 박영희
영업팀 - 김철수
영업팀 - 이민호
인사팀 - 최수아
```

이 정렬된 상태에서 선두 컬럼인 '부서' 를 이용하여 검색하면, 아래와 같이 검색할 수 있습니다. 

```
WHERE 부서 = '개발팀' AND 이름 = '박영희'
```

그렇다면 Database는 1차 정렬 기준인 부서의 개발팀으로 이동하여, 개발팀의 구역에서 박영희라는 이름을 가진 사람을 찾으면 된다. 

```
WHERE 이름 = '김철수'
```

하지만 위와 같이 조건절에 선두 컬럼인 부서가 아닌 이름으로 조건절을 설정한 경우에는 정상적으로 Index를 수행할 수 없습니다. 

우선적으로 부서별로 정렬되어 있는 값이 아닌 이름에 대한 조건절이기 때문에, Table 전체를 Full Scan 하는 비효율적인 방법을 사용할 수 있습니다.

### Index 사용 불가능 조건

이렇게 효율적으로 사용할 수 있는 Index 이지만, Index를 사용하지 못하는 조건도 분명 존재합니다. 조건절에 내/외부적 변형이 가해지거나, 부정형으로 비교된 조건절을 사용하거나 하는 등의 방법인데 대표적인 몇가지의 경우를 확인해보겠습니다. (이외에도 IN 연산자에서 속도가 저하될 우려, NULL 값을 저장하지 않는 경우에서의 Full Scan  위험, 결합 인덱스에서의 특정 인덱스까지만 유효한 부분 등 여러가지가 있지만 대표적으로 4가지만 알아 보겠습니다.)

1.  인덱스 컬럼에 외부적 변형이 가해질 때 (조건절에 WHERE UPPER(NAME) = 'test' 이런식의 조건절에 UPPER, + 등 연산자가 사용되어 변형이 가해질 때)
2.  인덱스 컬럼 내부에 변형이 가해질 때 (varchar 타입인데 숫자형을 넣어 DB 내부적으로 변형이 가해지는 경우)
3.  부정형 ( !=, <>, NOT IN) 으로 비교할 때
4.  LIKE 와일드카드가 조건절의 앞에 올때 (LIKE '%test')

이렇게 4가지 조건중에서 4번 조건으로 테스트를 진행해보겠습니다. 

```
EXPLAIN ANALYZE
SELECT * FROM users 
WHERE user_name = 'USER_50000';
```

기존 테스트 쿼리로 사용하던 위 쿼리에서 user\_name을 user\_name LIKE '%USER\_50000'; 으로 변경해서 진행해보겠습니다.

Count 결과는 두 쿼리가 모두 15개로 동일합니다. 

```
EXPLAIN ANALYZE
SELECT count(*) FROM users 
WHERE user_name LIKE '%USER_50000';
```

LIKE 인 조건절에 와일드카드를 앞에 기재할 경우 아래 Plan 정보와 같이 Table Full Scan을 하게 되므로, Index 가 사실상 무용지물이 됩니다.

## 마무리

이렇게 Index를 활용하여 Tuning을 진행할 수 있는 포인트를 공부해보았습니다. 하지만, 때로는 Index Range Scan보다 Full Scan이 빠른 경우도 존재합니다.

만약, 조회 결과가 전체 테이블 데이터의 약 20~25%를 차지할 만큼 방대한 양이라면 옵티마이저는 Index Scan을 수행하는 것 보다 Table Full Scan이 더 효율적이라고 판단할 수 있습니다. 

Index Scan이 튜닝에 많은 부분을 차지하는 것은 부정할 수 없는 사실이지만, 때로는 Table Full Scan도 효율적인 방안이 될 수 있다는 것을 알고 있으면 좋을 것 같습니다.
