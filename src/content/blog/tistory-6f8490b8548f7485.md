오늘은 오라클 다음으로 가장 많이 사용하고 있는, 오픈 소스형 Database 중 하나인 제가 현재 운영중인 시스템의 데이터베이스인 MySQL의 아키텍처를 공부하며 기록해보려고 합니다.

RBMDS에 대한 아키텍처는 양이 많기 때문에 여러번에 걸쳐서 포스팅하려 하고, 이번에는 기본적인 아키텍처의 전반적인 설명을 간단히 진행하겠습니다. 

* * *

![](__MEDIA__/87939b7ac203fe2efe19ea1f60a58ae5be9e82599f0a61a9bf152b510283a081.png)

MySQL 전체 구조 ❘ 출처 : Real MySQL 1권

우선 MySQL 엔진의 전체 구조는, 일반 상용 RDBMS와 같이 대부분의 프로그래밍 언어로부터 접근 방법을 모두 지원한다. C API부터, JDBC, ODBC 그리고 .NET의 표준 드라이버를 제공하고 기타 다양한 서버에서 쿼리를 사용할 수 있게 지원한다.

위 서적에서는 MySQL 엔진과 Storage 엔진 2가지로 MySQL 엔진을 구분하였다.

MySQL 엔진 

*   클라이언트로부터의 접속 및 쿼리 요청을 처리하는 커넥션 핸들러와 SQL 파서 및 전처리기, 쿼리의 최적화된 실행을 위한 옵티마이저가 중심을 이루고, 표준 SQL 문법을 지원하여 타 DBMS와 호환이 가능하다.

커넥션 핸들러 

*   클라이언트의 접속 요청을 처리하고 관리하는 주체, 각 클라이언트의 연결마다 독립적인 스레드를 할당한다.

SQL 인터페이스 & 파서

*   사용자가 보낸 SQL 문법의 오류를 체크하고, SQL을 서버가 이해할 수 있는 형태인 트리 형태 구조로 분해한다.

전처리 (Preprocessor)

*   파서가 만든 트리 구조를 기반으로 테이블 이름이나 컬럼 이름이 실제로 존재하는지, 접근 권한이 있는지 등 논리적인 오류를 확인한다.

옵티마이저 

*   사용자가 요청한 쿼리를 어떻게 처리해야 가장 빠르고 효율적일지 결정합니다. (ex. 어떤 인덱스를 사용할지, 어떤 순서로 조인할 지)
*   단, 옵티마이저가 제공하는 쿼리 플랜이 항상 옳을수는 없습니다. 통계 정보를 갱신해야할 필요도 종종 생깁니다. 

* * *

Storage 엔진

*   요청된 SQL 문장을 분석하거나, 최적화하는 등 DBMS의 두뇌에 해당하는 처리를 수행하고, 실제 데이터를 Disk Storage에 저장하거나, Disk Storage에 저장된 데이터를 읽어오는 부분은 Storage 엔진이 전담한다.
*   MySQL 서버에서 엔진은 하나지만, 내부의 스토리지 엔진은 여러 개를 동시에 사용할 수 있다.

핸들러 API

*   MySQL 엔진의 쿼리 실행기에서 데이터를 쓰거나 읽어야 할 때는 각 스토리지 엔진에 쓰기 또는 읽기를 요청하는데, 이러한 요청을 핸들러 요청이라고 하고, 여기에 사용되는 API를 핸들러 API라고 한다.
*   이 핸들러 API를 통해 데이터의 읽기/쓰기를 요청한다.

* * *

위에 출력된 전체 MySQL 구조를 따라서, 데이터를 불러오거나 변경하는 작업을 하게 되면 Buffer Pool 과 Dirty Page를 알아야 한다.

![](__MEDIA__/7f8e15a039bc36697bfd285efa5576b770f8e85b17cc52fdc3bcaa91492cff22.jpg)

Buffer Pool 과 Redo Log ❘ 출처 : https://hidetatz.medium.com/how-innodb-writes-data-on-the-disk-1b109a8a8d14

MySQL InnoDB는 데이터를 변경할 때에, 디스크의 데이터 파일을 변경하는 것이 아닌, 메모리 영역의 Buffer Pool 에서 변경합니다.

*   Buffer Pool : 데이터페이지 (16KB)를 캐싱하는 메인 메모리 공간, 테이블이나 인덱스 데이터를 캐싱합니다. 
*   Dirty Page : 사용자가  UPDATE, INSERT 등 데이터 변경을 실행하면, 메모리 상의 내용은 변경 되었지만 아직 디스크에 반영되지 않은 메모리와 디스크의 일치하지 않는 페이지를 의미합니다. (실제 데이터 파일에는 변경사항이 반영되지 않음.)

만약, Dirty Page가 메모리에만 있는채로 Database가 Down 된다면, 변경된 데이터는 사라집니다. 이를 막기 위해 MySQL 에서 사용하는 로그가 Redo Log입니다. WAL (Write Ahead Log) 원칙이 적용됩니다.

*   Redo Log : 데이터 페이지의 변경된 물리적인 내용을 기록합니다. 

Redo Log와 Dirty page는 Memory 공간이 아닌 언젠가 Disk 공간으로 가야합니다. 이를 Check Point라고 하며, Buffer Pool 에서 데이터가 바로 Disk 공간으로 가는것이 아닌, 동기화 상태로 유지합니다. 

* * *

이렇게 간단하게, MySQL의 엔진 설명과 데이터 조회 및 변경시에 필요한 Log 아키텍처에 대해서 살펴보았습니다. Redo Log와 MySQL의 Binary Log는 유사해보여도 차이점이 굉장히 많습니다. 다음에는 이 차이점에 대해서 공부하고, Buffer Pool을 어떻게 설정하느냐에 따라 성능에도 큰 차이가 발생하는데 이 부분도 아키텍처적인 관점에서 공부해보려고 합니다.
