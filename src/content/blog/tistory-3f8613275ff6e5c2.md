AWS MySQL 인스턴스를 최초 생성할 때, 스토리지를 할당하게 된다. 신규 서비스를 오픈하기 전이나, 안정화가 이루어지기 전 스토리지를 여유롭게 할당하게 되는데, 이렇게 할당된 스토리지는 비용이 굉장히 많이 청구되게 된다. 나중에 시스템이 안정화되고 과금되는 금액의 절감을 위해 스토리지 다운사이징을 진행하려고 하면 최초에 할당한 스토리지는 줄일 수가 없다는 것을 알게 될 것이다.

최소로 할당된 스토리지와 최대로 할당된 스토리지의 가격 차이는 인스턴스 유형별로 차이가 있으나, 많게는 수십, 수백배까지 과금에서 차이가 발생한다. 여기서 발생하는 과금을 줄이기 위해서는 어떻게 해야할까? 

1.  동일한 유형의 인스턴스에서 스토리지 크기만을 수정한 뒤 DMS 를 활용하여 데이터 마이그레이션을 진행한다.
2.  Blue/Green 배포를 활용하여 동일한 인스턴스 복제본을 만든 뒤, 스토리지 크기를 줄여 전환을 진행한다.

이렇게 2가지 방법을 고려할 수 있다. 여기서 오늘은 2번 Blue/Green 배포를 활용하여 동일한 인스턴스 복제본을 만들고 스토리지 크기를 줄여 전환을 진행하려고 한다.

우선 Blue/Green 배포 방식이란?

\- Database 엔진 버전 업그레이드, 파라미터 그룹 변경, 스토리지/사이즈 변경 등 데이터베이스 변경 시 다운타임과 리스크를 최소화 하기위해 도입된 기능이다. 

\- 기존 인스턴스인 Blue 인스턴스를 기반으로 동기화된 복사본 Green 인스턴스를 생성하고, 그린 환경에서 변겅 작업을 수행한다.

\- 인스턴스의 실시간 동기화가 가능하며, 유실되는 데이터 없이 최소 다운타임으로 업그레이드가 가능하다.  

\- Green 환경에서 변경이 완료되면 Switchover 하여 Green이 Main 인스턴스가 되고, 기존 Blue 인스턴스는 보조/백업 상태로 변경된다.

\- 엔드포인트의 변경이 없으며 기존 Blue 인스턴스는 \_old 형태의 인스턴스로 전환된다.
