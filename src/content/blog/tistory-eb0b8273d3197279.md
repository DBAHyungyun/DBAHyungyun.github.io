안녕하세요 어제는 이전 글에 뒤이어서 k8s를 사용하여 PostgreSQL DB를 자동으로 관리하고 pod 단에서 관리할 수 있게끔 실습 및 개념 공부를 해보겠습니다. 

지난 글에서는 EC2에 Docker를 설치하고, postgres:17 이미지로 컨테이너를 두 개(pg-test, pg-test2) 띄워서 인스턴스가 정상적으로 생성되는지 확인하였습니다. 오늘은 여기에 이어서 같은 EC2에 k3s를 설치하고, Docker 컨테이너와는 별개로 PostgreSQL을 Pod 단위로 관리하는 방법을 실습하려 합니다.

### 개요

지난번 글에서는 Docker에서 컨테이너를 생성하였는데 k8s는 항상 이미지를 기반으로 새로운 컨테이너를 처음부터 만듭니다. 즉 지금부터 할 실습은 기존에 생성한 컨테이너를 옮기는 것이 아니라, **지난 글에서 만든 것과 동일한 스펙의 PostgreSQL을 K8s Pod로 새로 생성하는 것**입니다.

그리고 이번 실습에서는 k8s가 아닌 k3s를 사용하여 진행하려고 하는데요. k3s 는 k8s의 배포판으로 개발/학습용에 적합한 도구입니다. 실습하고 학습하기에는 큰 차이가 없어서 적은 스펙의 k3s를 사용하여 실습하였습니다.

### K3s 설치 및 서비스 제어

우선 k3s 를 설치합니다. k3s는 콘솔 명령어로 간단하게 설치가 가능합니다.

```
curl -sfL https://get.k3s.io | sh -
```

설치가 완료 되었다면, 아래 명령어로 실제 k3s가 정상적으로 올라왔는지 확인합니다. 아래 사진처럼 정상적으로 동작하는 명령어가 나온다면 설치 완료입니다. 

```
sudo k3s kubectl get nodes
```

![](__MEDIA__/f839e0424ffcc6d71f409cda89f142d688296864591b4e7c47c751d02ab38775.png)

기동 중지 및 상태 확인 명령어는 아래 명령어를 참고하면 되고, 보통은 Alias 별칭을 등록하여 간편하게 사용하는 편입니다.

기본적으로 위 처럼 설치 스크립트로 설치하게 될 경우 enable이 적용되어 있어서 EC2가 재부팅 되면 

```
sudo systemctl start k3s      # 기동
sudo systemctl stop k3s       # 중지
sudo systemctl restart k3s    # 재시작
sudo systemctl status k3s     # 상태 확인
```

docker에서 pg-test, pg-test2 처럼 용도에 따라 DB를 구분하기 위해 k3s에 전용 네임 스페이스를 생성해줍니다.

```
kubectl create namespace pg-lab
```

Docker에서는 평문으로 패스워드를 관리하였지만, 쿠버네티스에서는 비밀번호를 Secret로 분리하여 패스워드를 관리하였습니다.

생성된 패스워드는 secretKeyRef 값을 참조하게 되고, 환경변수에서 평문으로 암호를 저장하던 것을 개선하였습니다.

```
kubectl create secret generic pg-secret -n pg-lab \
  --from-literal=POSTGRES_PASSWORD=test1234
```

### PostgreSQL  배포하기

pg-statefulset.yaml 파일을 생성하여, 해당 파일 안에 아래 옵션을 지정하여 생성했습니다.

```
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: pg-test
  namespace: pg-lab
spec:
  serviceName: pg-test
  replicas: 1
  selector:
    matchLabels:
      app: pg-test
  template:
    metadata:
      labels:
        app: pg-test
    spec:
      containers:
        - name: postgres
          image: postgres:17
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_DB
              value: testdb
            - name: POSTGRES_USER
              value: postgres
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: pg-secret
                  key: POSTGRES_PASSWORD
          volumeMounts:
            - name: pgdata
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: pgdata
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi
```

생성된 yaml 파일을 바탕으로 배포를 진행하였습니다. 명령어는 아래와 같습니다.

```
kubectl apply -f pg-statefulset.yaml -n pg-lab
```

![](__MEDIA__/94bbbbe28251942b6aa18d6adce2b6a75f93b1766a5adef267815e1d81784565.png)

추가로 위 사진처럼 실제 k3s가 정상적으로 설치되고 PostgreSQL이 정상적으로 운영되고 있다면 아래 명령어로 상태 확인을 진행합니다. 

```
kubectl get pods -n pg-lab
kubectl get pvc -n pg-lab
```

Pod의 Status가 Running, PVC가 Bound 상태면 정상이고 k3s는 기본 StorageClass인 local-path를 가지고 있어서 별도 설정 없이도 PV가 생성됩니다. 

PV란, PersistentVolume 의 약자로 실제로 존재하는 저장 공간입니다. k3s에서는 기본 StorageClass인 local-path가 EC2의 로컬 디스크 특정 경로를 설정하여 PV로 만들어줍니다.

PVC란, PersistentVolumeClaim 의 약자로 저장 공간을 할당 해달라고 요청해주는 요청서입니다. 위의 Statefulset 에서 기재했던 volumeClaimTemplates 부분이 PVC를 자동으로 생성해 달라는 일종의 선언입니다. 

### 설치 확인 및 DB 접속

이렇게 확인이 되었다면 DB 접속을 진행하면 됩니다. 아래 명령어로 접속하고 Select Version(); 명령어로 설치 된 DB의 버전을 확인하겠습니다. 

```
kubectl exec -it pg-test-0 -n pg-lab -- psql -U postgres -d testdb
```

### 마무리

오늘은 지난 글에서 Docker로 띄웠던 PostgreSQL을 K3s 환경에서 StatefulSet과 PVC로 재현하고, Pod 안에 직접 접속해서 테이블을 만들고 데이터를 넣어보는 것까지 진행했습니다.

특히 처음엔 "기존 Docker 컨테이너를 K8s가 관리하도록 옮기면 되는 것 아닌가"라고 생각했는데, 실습을 진행하면서 이게 정확한 개념이 아니라는 걸 알게 됐습니다. Docker 컨테이너와 K8s Pod는 완전히 독립된 실행 단위이고, K8s는 항상 manifest에 적힌 이미지를 기반으로 새로운 Pod를 만든다는 걸 직접 확인할 수 있었습니다.

*   Docker 컨테이너와 K8s Pod는 이관 관계가 아니라 각각 독립된 실행 단위이다.
*   StatefulSet은 Pod마다 고유한 이름(pg-test-0)과 전용 PVC를 보장해서, Pod가 재시작돼도 같은 이름으로 같은 PVC를 다시 마운트한다.
*   PV/PVC는 Pod의 생명주기와 분리되어 있어서, Pod가 사라지고 다시 생겨도 데이터는 그대로 유지된다.
*   비밀번호 같은 민감 정보는 Secret으로 분리해서 관리하는 게 Docker의 평문 환경변수 방식보다 안전하다.

오늘 확인한 PV/PVC의 데이터 영속성 특징을 기억해두고, 다음번에는 여러 개의 워크로드를 함께 다루는 쿠버네티스 환경에서 DB 자동화를 어떻게 구성할 수 있을지 공부해보려고 합니다.
